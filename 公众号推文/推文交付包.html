参加麦当劳 MCP 开发大赛，我被 92.3% 的假故障卡住了

一、引子：官方示例是"套餐推荐助手"，缺口在热量

2026 年 10 月，麦当劳中国开放了官方 MCP 服务（mcd-mcp，Bearer Token 鉴权，覆盖时间、门店、订单、菜单、营养、报价、下单全链路的 20 多个原子工具），并联合 WorkBuddy 发起程序员创意开发大赛，面向开发者征集基于这套 MCP 的 Skill。官方给的方向示例里有"套餐推荐助手"——而它最容易做成菜单的另一种排列：拉菜单、按分类罗列、按价格排序。这样的推荐缺一个约束维度：热量。对一个想控制单餐摄入的人来说，没有热量约束的推荐等于没有推荐。

于是我的参赛项目「热麦卡路里」选题定为：以订单为起点的热量估算与餐段档位套餐推荐。输入一笔真实订单（或指定餐段），输出总热量、与该餐段热量档位的对比、以及档位内的替代组合。14 天开发周期，12 次提交，7 条架构决策记录（ADR），常见订单集名称匹配率 92.3%（验收线 90%）。

"这单多少热量"这个问题，用五步调用链描述：

  1. now-time-info 获取当前时间，判定餐段；
  2. query-order（或 order-list）读取订单；
  3. 本地展开套餐子项、剥离加料描述；
  4. 拉取营养表，逐项匹配热量；
  5. 与该餐段的热量档位比较，输出结论。

这五步没有任何一步可以省略，也没有任何一个现成工具能替代。这篇记录：核心能力与工作流、架构与项目结构、核心算法，以及接口暴露出的五个陷阱。

二、核心能力与工作流（A–F）

作为可直接对话的 Agent Skill，它对外提供六项能力：

  • 订单热量估算 — 按 comboItemList 展开套餐，「加…(加)」类加料剥离且热量不计入并明确告知；匹配不上的项标注「热量未知」，合计改口为「≥ N kcal」，绝不按 0 计算。
  • 餐段识别 — 默认按当前时间判定（早餐 / 午餐 / 随便吃吃 / 晚餐 / 宵夜），也支持显式指定；门店实际时段优先于固定兜底（各店不同，且宵夜存在跨零点段）。
  • 档位推荐 — 按「餐段 + 档位（轻量 / 标准 / 吃饱）」枚举当前可售组合（1 主食 + 0~1 小食 + 0~1 饮品），四种排序：最接近档位 / 蛋白质更高 / 钠更低 / 价格更低。
  • 替换建议 — 整单高于该餐段标准档时，给出更轻的替换组合与「少多少 kcal」的对比。
  • 历史复盘与一键导入 — order-list 原始响应自动脱敏落盘，逐单估算热量，输出热量排行、超标准档的单子、平均热量与未知项占比。
  • 安全下单 — 查券（只标注，不参与排序）→ 报价 → 必须展示金额并获得用户明确确认 → 创建订单，返回支付链接由用户自付。

六项能力对应六条对话工作流，每条都有明确的触发语：

阶段触发语说明
A 订单热量估算「这单多少热量？」订单号 → 展开套餐 → 逐项匹配营养表 → 整单合计 + 档位对比
B 档位推荐「想吃 300 大卡左右的早餐」取该餐段菜单 → 枚举组合 → 按档位 ±12% 筛选 → 展示 Top 3–4
C 替换建议「昨天那单偏高」高于标准档则切标准档，输出替换组合 + 少多少 kcal
D 一键导入历史订单「导入我的历史订单分析热量」order-list 原始响应 → 自动脱敏落盘 → 逐单热量 → 排行与汇总
D2 历史订单复盘「我最近都吃了些什么」已脱敏样本 → 逐单热量 → 餐段比对 → 排行与汇总
E 下单用户明确要求查券（仅标注）→ 报价 → 确认闸门 → 创建订单
F 全量目录离线兜底多份菜单快照聚合为 catalog.json / nutrition-gaps.json

其中 E 是唯一产生资金动作的流程，闸门设计见第七节；F 生成的目录只用于离线匹配与兜底——推荐候选必须取自当次 query-meals 实时返回，价格随餐段浮动，目录价会过期。

三、范围与能力收窄

官方连接器实际提供 20 多个工具——券包、积分账户、团餐、积分商城一应俱全。本项目主动只使用了 11 个，优惠券只做标注、不介入核销。

收窄的理由：每多接一个工具，就多一份字段口径要对齐，多一块合规面。最小可行不是偷懒，是控制不确定性。

同时明确不做三件事：医学与减重建议（热量只作为估算参考）、自定义套餐换品交互（接口自 1.0.5 起已支持，本期收窄）、历史订单批量分析（能力存在，但会引入额外的匹配与校准成本）。这三条"不做"写进了 PRD，后面每一次需求扩张都拿它对表。

五、三个核心算法

5.1 名称匹配：四级，且必须保护"不知道"

跨来源匹配一律以归一化名称为主键，code 只在同一个来源内部做校验。原因很直接：同一个可乐，在菜单里是 9900008751，在套餐子项里是 3050 或 3100，跨来源对不上。

归一化规则：剥离品牌前缀、括号内容、多余空格，以及 -poolN 后缀与「加……(加)」加料描述。加料热量不计入并明确告知用户；减料与换料特调沿用基础商品热量，文案说明方向（加料低估、减料换料高估）。

四级匹配：

  • L1 exact — 归一化后精确命中；
  • L1.5 exact-qty — 保留数量后缀的原始键精确（为什么需要这一级，见坑 3）；
  • L2 alias — 别名表 alias.json，只收录归一化无法直接命中的映射（当前仅 2 条）；
  • L3 prefix — 前缀匹配 + 长度窗口剪枝，控制误匹配范围。

关键兜底：匹配不上返回 UNKNOWN，绝不按 0 计算，合计写成「≥ N kcal（实际会更高）」；名称歧义（可乐、薯条、新地、派等缺规格项）列出候选项让用户确认，不做猜测。

UNKNOWN 不是防御性冗余，而是由数据现状决定的。营养表对当前在售单品的覆盖率实测只有 44.4%：179 个商品（89 套餐 / 90 单品）中，单品命中 40、规格歧义 13、未收录 37，缺口集中在季节限定与联名新品（北非蛋风味系列、爆脆星星堡、德克萨斯风味三层肉霸堡、举杯邀月柚桂茶等）。在这种覆盖率下，"按 0 算"不是小误差，是系统性低估。

缺口处理也是工程化的：未收录与歧义项落盘到 data/nutrition-gaps.json（含 origin=history-order 标记的历史已下架品），作为补录与反馈清单，避免每次重新发现。历史订单的 unknown 项由 mcd_catalog.collect_history_gaps() 自动展开登记，不靠手工维护。

5.2 组合枚举：先归类，再剪枝

推荐不是搜索，是枚举加筛选。

品类判定用三级兜底：菜单分类名映射 → 套餐 rounds 反查（借助 isDefault=1 的默认搭配反查单品品类与默认规格）→ 关键词规则（category-rules.json）。之所以要三级，是因为接口的 category 字段时有时无（实测两个套餐详情，一个有、一个没有）。

组合规则：正餐与宵夜为「1 主食 + 0~1 小食 + 0~1 饮品」，主食位只取 tags 含「单品」的成品——tags 含「套餐」的商品不得进入主食位，否则会与小食、饮品重复计算；下午茶不含主食，由 1~3 个小食、甜品、饮品拼成，其中饮品最多 1 个。菜单中混入的非食品条目（实测有「按摩捶痒痒挠」「风味酱」）一律剔除。

筛选与排序：按档位目标 ±12% 过滤，四种排序——最接近档位（near）/ 蛋白质更高（protein）/ 钠更低（sodium）/ 价格更低（price）；展示 Top 3–4 组，每组含热量、蛋白、脂肪、碳水、钠与参考价；已读取订单时附「较本单 ±kcal」。档位内无解就提示换档位，绝不放宽筛选范围——放宽一次，档位这个概念就失效了。枚举部分做了预剪枝，把 O(n²) 降到线性。

5.3 餐段判定：实测优先，处理跨零点

餐段来源的优先级：用户显式指定 > 订单自带信息（createTime / expectedDaypart，订单是历史事实，不该用当前时刻去判）> 门店 reservationTimeOptions 逐店解析 > PRD 固定值兜底。

逐店解析是必须的：各店时段差异很大，早餐最早 05:14 起供应，宵夜段约 22:14 起，部分门店跨过零点到 04:45。「宵夜」是单列的第五餐段，档位 300/450/600 kcal，不并入晚餐——这是开发中一个被明确拍板的决策（ADR-003），代价是需要处理跨零点的时段判定。

六、五个接口陷阱

坑 1：query-meals 没有 daypart 字段

想按餐段取菜单，文档里找不到任何餐段参数，返回值中也没有。最终解法：传 reservationDate 为"该餐段的代表时刻"，让接口按时间去命中餐段。此外分类里还可能出现 meals{} 中不存在的 code（夜市 9900000881），必须保留 UNKNOWN 兜底。

坑 2：字段名不一致，92.3% 的"假故障"

批量复盘历史订单时，超过九成商品匹配不上营养表，整单标满 UNKNOWN。

# order-list   →  套餐子项名称字段
{ "name": "板烧鸡腿堡" }

# query-order  →  同一个东西，字段却叫
{ "productName": "板烧鸡腿堡" }

展开函数只认后者，所有套餐子项被读成空字符串。兼容两种字段后，未知率从 92.3% 降到 10.3%。这不是数据源的问题，是解析层的问题——当某个指标差得离谱时，先怀疑自己的解析，再怀疑数据。

坑 3：「麦乐鸡5块」丢了 213 kcal

归一化规则"剥掉数字规格后缀"本意是让「可乐中杯」与「可乐」对上，但它顺手把「麦乐鸡5块」的"5块"也剥了，匹配到了另一个商品：整单从 715 kcal 变为修复后的 928 kcal，差 213 kcal。修法即 L1.5 exact-qty：用未剥后缀的原始键先做一次精确匹配。

凡是"为了让匹配率好看"而做的归一化，都必须回头验证它有没有误伤；数量后缀这类承载语义的后缀，与规格后缀必须区别对待。

坑 4：rounds[].name 不是品类

读套餐组成时，round1 的 name 写着「新升级巨无霸」，看起来像主食位。拆「巨无霸三件套」时发现 round1 的 name 依然叫「新升级巨无霸」——它只是轮次的名字，与品类无关。真正的品类在 category 字段，而该字段可能缺失（实测 9900004064 有、9900005466 无），缺失时按名称反查或关键词兜底。

坑 5：金额单位是分，换品不等于特调

  • calculate-price 返回的金额单位是分，展示前必须 ÷100；
  • 到店下单（orderType=1）时 create-order 必传 takeWayCode，取自同一次报价返回的 takeWayList[].code；外送（orderType=2）不传；
  • 换品发生在 rounds[].choices 层，用 diffPrice 计算差价（如小食轮 4 选 1、饮料轮 25 选 1）；特调（去冰、不要生菜、换燕麦奶 +2 元）看 supportModify / modification。两者不可混用，且含 unselectedKey 的特调组必须将 selectedKey 与 unselectedKey 同时传给报价与下单。

两条附赠实测结论：同一商品在不同餐段价格不同（麦咖啡奶铁早餐 13.9 / 午餐 9.9；马苏里拉拉丝芝士条午餐 16 / 夜市 11），部分商品带「随单购麦金卡优惠」标签——任何报价与价格排序只能用当次 query-meals 返回值，缓存目录价必然过期；菜单与套餐子项中同一商品 code 不同，跨来源匹配必须以归一化名称为主键。

七、下单流程与确认闸门

下单是唯一产生资金动作的流程，设计为五步，闸门不可绕过：

  1. query-store-coupons 查券，仅标注，不参与排序；
  2. calculate-price 报价，金额 ÷100 转元；
  3. 完整展示金额，以明确问句收尾，等待用户确认——未获确认绝不调用 create-order；
  4. 确认后 create-order（到店取第 2 步返回的 takeWayList[].code 作 takeWayCode）；
  5. 返回支付链接，由用户自付；Skill 不代付、不轮询支付状态。

闸门约束写在 docs/order-flow.md 与 SKILL.md 两处，属于文档级 + 流程级双重约束，而非依赖模型自觉。

  • CR-001 — 订单餐段忽略了 expectedDaypart，历史订单被一律误判为午餐档；

九、经验沉淀

  1. 先怀疑自己的解析层。指标差得离谱时，大概率是字段名、单位、编码这类低级问题，不是数据源不行。坑 2 的 92.3% 与坑 3 的 213 kcal 都属于这一类。
  2. 让计算可离线回归。把逻辑从对话和网络中剥离，才有可反复验证的评测集。92.3% 这个数字之所以可信，是因为它在无网络环境下可复现。
  3. 给"不知道"留一条合法路径。UNKNOWN 是一等公民，而不是异常。在覆盖率 44% 的系统里，容错设计比算法优化更重要。
  4. 默认值要显式传递。CR-001 与 CR-002 同源。跨函数的隐式默认参数是 bug 最集中的藏身之处。
  5. 主动收窄能力。接口提供 20+ 工具，使用 11 个即可。每多接一个，就多一份需要对齐的口径与合规面。
  6. 把"怎么用 MCP 的"写成可核验的文档。这次大赛的 MCP_INTEGRATION.md 与 workbuddy.md 要求恰好逼出了这件事：用了哪些 Tool、按什么顺序调、业务价值是什么、开发过程长什么样，全部落盘。这套材料不是为了应付核验——它本身就是项目文档里最有用的两份。

十、结语

回到开头：能力是现成的，但"从拿到数据到回答用户一个问题"之间的编排，工具不会替你做。

MCP 把能力拆成原子，编排的责任落到开发者身上。编排的难点不在调通接口——调通只要几分钟——而在于为每一处"接口没说清楚"的地方做出决定，并为这些决定建立可验证的机制：匹配器有 UNKNOWN 兜底，下单有确认闸门，评测有离线回归，数据有快照可回溯。

接口的返回值比想象中更不可信，而系统要在这个前提下依然可靠——这是这次参赛给我的最大收获。
