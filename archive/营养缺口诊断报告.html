一、先分清两类「滞后」

把两件事混在一起谈，会导致优化方向跑偏：

类型根因数量能否自愈
A · 数据源滞后 官方 list-nutrition-foods 未收录季节/联名新品（北非蛋系列、龙焰堡、蘸酱炸鸡等） 40 项 否 接口不给数据，算法再强也无用
B · 匹配器失配 营养表有该条目，但菜单名缺规格（「可乐」→ 中/大/小杯） 13 项 是 可用证据消解

关键判断

覆盖率 44.4% 里，40 项是「接口根本没这条数据」，仅 13 项是「有数据但名字对不上」。因此「优化匹配器」的收益天花板很低；正确的投入方向是消解 B 类歧义 + 接受 A 类并明确降级策略。

二、方法论：接口实测（先证伪，再动手）

不靠推测，直接调用官方接口看原始响应字段。排查了全部四个潜在营养来源：

接口最深层字段含营养字段？
list-nutrition-foodsproductName / energyKj / energyKcal / protein / fat / carbohydrate / sodium / calcium是 · 唯一来源

query-order / order-listproductCodes / productName / quantity / comboItemList / realTotalAmount否

结论：自采集路径不通

原先设想的「从套餐详情/订单接口回捞营养值」方案作废。官方 MCP 里营养数据只有 list-nutrition-foods 一个出口，且本地缓存（160 条）与线上完全一致——不是缓存旧了，是源头就这些。

补充：query-meal-detail 的字段文档里还列了 modification / supportModify（特调）与 image，但均与营养无关。

三、突破口：code 级规格证据法

实测中发现一条此前未被利用的线索：菜单接口与套餐详情接口共享商品 code，同一 code 在同一门店唯一标识一个商品。

原理

菜单里商品写作「玉米杯」（缺规格，code 4437），而某个套餐的选项里同一个 code 4437 写作「小杯玉米杯」。因为 code 唯一，即可反推：4437 = 小杯玉米杯。这是一条硬证据，不是猜测。

验证强度：4810 在 35 个套餐中全部名为「中薯条」、507409 在 74 个套餐中全部名为「麦咖啡™冰奶铁中杯」——一致率 100%，零例外。

据此新增脚本 scripts/mcd_spec_evidence.py，把证据按可靠性分五级，只有最高级才允许自动落库：

等级判据处置
A菜单名未命中，且是套餐规格名的真子串（「玉米杯」⊂「小杯玉米杯」）写入 alias.json#defaults
B菜单名带多值标记（「（冰/热）」）或含冰热差异保持歧义，交用户选
C1现网命中条目 ≠ 套餐证据 → 疑似错误映射报告，不自动改
C2同一 code 在不同套餐出现多个规格禁止补录
D已命中且与证据一致无需处理

判据红线：「冰/热」是做法，不是规格

冰奶铁 148 kcal / 热奶铁 186 kcal，差 38 kcal。菜单名省略冰/热时不能替用户锁定，否则温度一说错、热量直接偏低或偏高。故涉及冰热的证据一律归 B 级、保持歧义。

5.2 估算模型 · 三个方案供选择

对 A 类缺口（官方不收录的新品），可行路径只有三条，各有取舍：

方案做法优点风险 / 成本
A · 同品类锚定估算 按品类锚定同类已知品（如「北非蛋风味猪柳蛋麦满分」锚定「猪柳蛋麦满分」）做估算，显式标注「估算值」 覆盖率提升最大 合规风险 与红线「不凭记忆给热量数字」张力大，须加标注 + 不进推荐候选
B · 只优化降级展示 未知项统一显示「热量未知」，但给出下界与品类提示（如「这是一款汉堡，通常 300–500 kcal」） 零合规风险；立即可做 不提升数值覆盖率
C · 人工补录表 新增 data/nutrition-manual.json，从官方包装/官网人工录入常见新品，标注来源与日期 最准，数据最权威 需人工维护，新品上架有滞后

建议：B + C 组合，A 暂缓

先用 B 把未知项的体验做扎实（下界 + 品类提示），再用 C 逐步补录高频新品。方案 A 涉及「凭空估算热量」，与 PRD §8 合规条款冲突，建议仅在用户主动要求且明确标注的前提下考虑。最终口径需你拍板。
