S1

接口勘察结论（实测）

以下均为本次真实调用返回，非文档推断。样本时间 2026-10-09 23:36:31 GMT+8（夜市时段），门店 3570190。

M-01query-meals 返回结构

  • 顶层 data.categories[]：分类名 + meals[].code + meals[].tags[]
  • 顶层 data.meals{}：code → name / image / currentPrice / originalPrice / discountType / canWithOrder / withOrder
  • 无 daypart 字段，无「分类 id」
  • 分类名示例：鸡肉汉堡/卷、小食甜品/其他、饮品、麦咖啡™、500大卡套餐、蘸酱炸鸡、开心乐园
  • 返回的是调用时刻可售的菜单（23:36 返回夜市菜单，无早餐品）

M-02tags 是可用的结构化信号

  • "套餐" 标记组合商品（如「板烧鸡腿堡三件套」）
  • "单品" 标记可单买的成品（如「巨无霸」「麦辣鸡腿汉堡」）
  • 其余为营销标签：上新、爆款、麦金卡、100%纯牛肉、冰淇淋、冷饮/热饮
  • 用途：拼装组合时，主食位只取 单品，避免推到已含小食饮料的套餐造成重复计算

M-03query-meal-detail 的 rounds 名称 = 权威品类

rounds[].name 实测值：
  1. "主食任意选"
  2. "选择套餐内小食"
  3. "选择套餐内饮料"
  • 每个 round 含 choices[].code/name/diffPrice/isDefault/supportModify/modification
  • 可用套餐默认搭配（isDefault=1）反查单品 → 品类映射，比名称关键词可靠得多
  • 无 daypart 字段（与 query-meals 一致）

M-04code 空间不一致，名称才是主键

  • 菜单中「可乐」code = 9900008751
  • 套餐内子项「可乐中杯」code = 3050，「可乐大杯」= 3100
  • 菜单中「鲜萃咖啡」= 520689，套餐内「大杯鲜萃咖啡」= 520688
  • 结论：订单/套餐子项与营养表的匹配必须以名称为主键，code 仅作辅助校验

S2

对 PRD v0.1 的关键修正

编号 D1–D7，均基于 S1 实测。D1–D3 为阻塞性修正，不采纳会直接导致功能不可用。

编号PRD 原假设实测情况修正方案影响
D1 §5：query-meals 返回含 daypart，可按其过滤餐段 响应中完全没有 daypart 字段；菜单本身即「当前时刻可售」 用 reservationDate（格式 yyyy-MM-dd HH:mm）传入目标餐段内的时刻，取该餐段菜单。见 T17 阻塞
D2 §6/F2：餐段为固定时段（早餐 06:00–10:29 等） 各店真实时段差异大，且存在第五餐段宵夜（约 22:14 起）；早餐最早 05:14 开始 解析门店 reservationTimeOptions 文本得到逐店时段表；固定值仅作兜底。宵夜并入「晚餐」档位或单列，需在 T15 决策 阻塞
D3 §6：品类（主食/小食/饮品）用名称关键词规则归类 + 模型补充 已有权威来源：① categories[].name ② 套餐 rounds[].name 直接写「主食任意选 / 小食 / 饮料」 改为三级：分类名 → 套餐 round 反查 → 关键词+模型兜底。命中率与可维护性大幅提升 阻塞
D4 §6 组合规则：主食 + 小食 + 饮品自由拼 候选池里 tags 含「套餐」的是组合商品，放主食位会与「+小食+饮品」重复计算 主食位只取 tags 含「单品」者；另剔除玩具、单卖蘸酱等非食品 高
D5 §12 待确认：query-meals / query-meal-detail 是否带图片字段 两处都有 image（menu-img.mcd.cn/.../MS_{code}_320.png 及 _600.png） 已解答。但依 PRD §8 合规要求，一律不使用，演示页用自绘占位 已解决
D6 §5 接口映射：隐含可用 code 关联数据 同一商品在菜单与套餐子项中 code 不同（可乐 9900008751 vs 3050/3100） 匹配主键统一为归一化名称；code 仅在同一来源内部使用 高
D7 §F1：加料热量不计入 实测 modification 多为减料/换料（去冰、不要生菜、换燕麦奶 +¥2），与「加料」性质不同 区分两类：加料（热量不计，会低估）／减料换料（沿用基础值，会高估）。文案分别说明方向 中
📌 建议同步回写 PRD D1–D7 建议在 T33 之前一并更新进 PRD v0.2，尤其是 §5 接口映射（删除 daypart 描述）、§6 组合规则（加入 tags 过滤与非食品剔除）、§12 待确认（Q1/Q2 划掉）。参赛时 PRD 与实现不一致会被扣分。

技术架构与模块拆分

Skill 本体以 SKILL.md + 一组无第三方依赖的 Python 脚本交付，在支持 MCP 的客户端里通过对话触发。所有外部数据经缓存层，避免触发 600 次/分钟的限流。

                       ↓

                       ↓
┌─ 计算层（Python 脚本，纯本地、无网络）───────────────┐
