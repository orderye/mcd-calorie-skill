# 下单确认流程与安全闸门（T25/T26/T27 产出）

> 本 Skill 的本地脚本**不做任何下单动作**。优惠券、报价、下单全部通过
> MCP 工具（`query-store-coupons` / `calculate-price` / `create-order`）在对话流中执行，
> 本文档定义执行顺序与不可绕过的闸门。

## 流程（PRD F6/F7）

```
① query-store-coupons   查当前门店可用券
        ↓  券只做「有可用券」标注，不参与热量排序（PRD §6）
② calculate-price       对用户选定的组合报价（含券）
        ↓  金额单位为「分」→ 展示前 ÷100 转元（v0.3）
        ↓  到店场景（orderType=1）返回值含 takeWayList（取餐方式，v0.3）
        ↓  ★ 闸门：完整展示金额（原价/优惠/应付），等待用户明确确认
        ↓  用户未确认 / 答复模糊（"嗯""再说"）→ 一律不进入下一步
③ create-order          创建订单，返回支付链接，用户自行支付
        ↓  到店（orderType=1）必传 takeWayCode，取自②的 takeWayList[].code（v0.3）
        ↓  外送（orderType=2）不传 takeWayCode
        ↓  本 Skill 不代付、不轮询支付状态
```

## 闸门实现约定（验收 §9：100% 下单发生在确认之后）

- 对话流中：展示报价后必须以明确问句收尾（"确认按 ¥XX 下单吗？"），
  只有收到肯定答复才调用 `create-order`。
- 报价信息必须包含：组合明细、原价、优惠、应付金额、门店与取餐方式。

## 错误分支（PRD §7）

| 情形 | 处置 |
|---|---|
| 401 Token 无效 | 提示用户检查 MCP Token 配置，不重试 |
| 429 限流（600 次/分钟） | 指数退避后重试一次，再失败则建议稍后再试 |
| 促销品查不到详情 | 降级为仅使用 query-meals 的名称与价格，热量按 UNKNOWN 处理 |
| 营养表失败/为空 | 仅提示稍后重试，**不凭记忆给热量数字** |
| 门店无合适组合 | 提示换餐段或档位，不放宽 ±12% 筛选 |

## 价格口径备注

- 推荐组合的参考价 = 菜单 `currentPrice` 直加，**未考虑套餐价差**（单点合计通常高于套餐）；
  与用户沟通时必须标注"参考价"。
- 替换建议的价格差在拿到真实订单金额（`query-order` 含金额字段，字段名待首个真实订单校准）
  之前一律显示"需按实付口径计算"，不得估算。
- `calculate-price` 返回的金额单位为「分」，须 ÷100 转元后再展示（v0.3）。
- 到店下单（orderType=1）的 `takeWayCode` 必须取自**同一门店、同一组合**的 `calculate-price` 返回 `data.takeWayList[].code`，不得跨订单复用或猜测（v0.3）。
